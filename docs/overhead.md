# 계측 수준별 오버헤드 (DESIGN §9.1)

> 이 결과는 **로컬 단일 머신**(Docker Desktop VM, CPU·메모리 limit 고정)에서 **처리 방식 간 상대 비교**를 위해 측정한 값입니다. 운영 환경의 처리 용량을 뜻하지 않습니다.

계측 수준 스위치(`off` / `metrics` / `full`, 계약 C6)가 app 에 얹는 비용을 한 번 재서 공개한다. 이 표는 수준을 고르는 참고값이고, **실험 결과 비교는 같은 계측 수준끼리만 한다**(DESIGN §3 원칙 3). 수준이 다른 두 실행은 이 표의 차이만큼 조건이 다르므로, 수준이 다른 실행끼리 strategy 를 비교하지 않는다. 오케스트레이터 비교 화면도 `instrumentation` 이 다르면 axis 로 지정하지 않는 한 비교 불가로 표시한다.

### 지표 출처

- **p50 / p99 / n / 처리량**: k6 summary(성공 요청만, `expected_response:true`). 처리량은 k6 실제 완료율이고 목표 도착률과 짝으로 적는다.
- **app CPU**: cAdvisor `container_cpu_usage_seconds_total`(compose 서비스 `app`, 활성 2대 합)의 rate. 구간은 본 실행(steps 「k6 본 실행」→「불변식 검사」) + 그 앞 8초다. cAdvisor 표본 간격이 5~10초로 고르지 않아 30초 구간만 보면 인스턴스 하나가 표본 1개일 때가 있어서(2차 탐색 12회 중 3회) 같은 도착률로 돌던 웜업 끝 8초를 더 본다. 단위는 코어(limit 합 2코어). `metrics`·`full` 에서는 prom-client `process_cpu_seconds_total` 과 교차 확인했고 차이는 0.03코어 이내였다(`off` 는 그 지표가 없다).
- **무효 판정**: 오케스트레이터 판정(k6 CPU 포화·스크레이프 누락 등) + 이 측정의 추가 조건 — dropped > 0, HTTP 실패 > 0, 실제 처리량 < 목표의 97%, 불변식 위반, app CPU > limit 합의 85%. "앱이 포화되지 않은 상태의 오버헤드"를 재려는 것이라 dropped 가 하나라도 있으면 뺐다.

### 읽는 법 (같은 기준 안에서만)

- **p50**: `metrics` 는 `off` 와 범위가 겹친다(저경합 1.51 vs 1.63, 고경합 1.64 vs 1.53). `full` 은 두 기준 모두 `off` 보다 0.3~0.5ms 높고, 저경합에서는 3회 범위가 겹치지 않는다(off 1.50~1.52, full 1.75~1.93).
- **p99**: 저경합에서 `full` 이 `off`·`metrics` 의 약 2배(7.2 vs 3.9·3.8ms)이고 범위가 겹치지 않는다. 고경합은 수준과 무관하게 반복마다 4~35ms 로 흔들려(행 하나에 락 대기가 몰릴 때 생기는 꼬리로 추정, 원인 미확인) 3회로는 수준 차이를 가를 수 없다. 고경합 p99 를 수준 비교 근거로 쓰지 않는다.
- **app CPU**: `metrics` 는 `off` 와 범위가 겹친다(저경합 0.52 vs 0.48, 고경합 0.50 vs 0.51코어). `full` 은 같은 처리량에서 약 0.2~0.25코어 더 쓴다(저경합 0.70 vs 0.48, 고경합 0.76 vs 0.51). 400 req/s 에서 limit 합 2코어의 20~41% 라 포화와는 거리가 있다.
- 저경합 `off` 는 r3 이 무효(dropped 47, p99 101ms 의 짧은 정지)라 2회 값이다. 다시 돌려 채우지 않았다.
- 처리량은 모든 유효 실행에서 목표 400 req/s 와 같다(open model 이라 포화 전에는 처리량이 도착률을 따른다). 그래서 위 지연·CPU 차이는 같은 처리량에서의 차이다.

"같은 머신·같은 limit·같은 계측 수준에서" 라는 조건이 붙지 않은 strategy 비교 문장에 이 숫자를 인용하지 않는다. 이 표의 숫자도 이 머신·이 limit·이 도착률에서만 뜻이 있다.

## 다시 재기

```
docker compose -f infra/compose/docker-compose.yml --profile obs --profile trace up -d --build
node scripts/overhead/run.mjs --explore --rates 300,500,600              # 탐색(선택)
node scripts/overhead/run.mjs --rate-low 400 --rate-high 400             # 본 측정 18회 → runs/_overhead/<시각>_main.{json,md}
node scripts/overhead/run.mjs --render runs/_overhead/<시각>_main.json  # 표만 다시 출력
```

app·계측 코드, limit, cpuset, 프로필, Docker Desktop 설정 중 하나라도 바뀌면 다시 재고 이 문서를 바꾼다.
