# 실험 노트 양식

> 실험 노트는 **사용자의 학습 기록**(예측 → 실측 → 원인)이다. 코드는 AI가 작성했고, 코드 실험실(DESIGN §10.4)의 `expected`(예상)와 `measured`(실측)는 노트의 예측·결과와 별개로 기록한다. 노트의 예측은 코드 실험실의 `expected`를 보기 전에 쓰는 것이 가장 좋다.
> 파일 위치: `docs/experiments/<YYYY-MM-DD>-<scenario-id>-<slug>.md`
> 규칙: **1~3절(가설·정상 상태·조건)은 실행 전에 커밋한다.** 결과를 본 뒤 예측을 고치지 않는다. 틀린 예측은 그대로 두고 7절에서 왜 틀렸는지 쓴다.
> 수치는 항상 "로컬 단일 머신, 처리 방식 간 상대 비교" 맥락으로 쓴다. 지연은 처리량과 짝지어, 퍼센타일은 표본 수와 함께.

```markdown

- 날짜: YYYY-MM-DD
- 시나리오: <id> / 비교 strategy: <a> vs <b> [vs <c>]
- 배치 ID: <batchId> (반복 3회) / 커밋: <git sha>
- 실험 종류: 비교 | 망가뜨리기(카오스) | 스윕 | 용량 산정

## 1. 가설 (실행 전)

- 예측: <무엇이 어떻게 될 것인가. 가능하면 방향과 대략적 크기(배수·순서)로.>
- 근거: <왜 그렇게 예측하는가 — 메커니즘 설명.>
- 반증 조건: <어떤 결과가 나오면 이 가설이 틀린 것인가.>

## 2. 정상 상태 (실행 전)

> 카오스·과부하 실험에서는 필수. "정상"을 측정 가능한 값으로 정의한다.

- SLI/기준: <예: 성공률 ≥ X%, p99 ≤ Y ms @ 도착률 Z req/s (기준선 실행 <runId>에서 측정)>
- 불변식: <이 시나리오의 불변식 목록과 기대값(대개 위반 0). 판정 근거는 DB 원장 행, k6 카운트는 보조 대조>

## 3. 조건 (실행 전)

| 항목 | 값 |
|---|---|
| 실행 프로필 (default / minimal) / 커밋 sha / 이미지 | |
| 앱 인스턴스 / LB | |
| 리소스 limit (app / PG / k6, cpuset) | |
| 풀 크기 / acquire 타임아웃 | |
| PG 설정 해시 / 주요 값 / observerConnections | |
| Redis 설정 (maxmemory-policy, appendonly·appendfsync) | |
| 타임아웃 (k6 요청 / 서버 요청 / 풀 acquire / statement / lock / idle in tx) | |
| DB 경로 (direct / pgbouncer) / proxy | |
| 데이터 크기 / 시드 / 분포 | |
| 부하 모델 (open/closed) / executor / 모양 | |
| VU 또는 도착률 / maxVUs / 기간 / 웜업(별도 실행) / think time | |
| 계측 수준 / PG 락 프로브 (on·off, 주기) | |
| coldStart / osCacheControlled | |
| 개입 (지연 주입 / 카오스 예약) | |
| k6 스크립트 (템플릿 / 편집됨 + 해시) | |

- 영향 범위(blast radius): <이 실험이 건드리는 것 — 어떤 컨테이너·데이터·다른 실행에 영향이 있는가. 로컬이라도 명시.>
- 중단 조건: <예: critical 불변식 위반 즉시 / SLO 번레이트 > N / 실행 시간 > M분 / 호스트 메모리 부족 경고>

## 4. 결과

**정합성**

| strategy | 불변식 | 위반 수 (r1 / r2 / r3) |
|---|---|---|

**유효성**

- 무효 실행: <없음 / runId와 사유(k6 CPU 포화 등)>

- 원장 vs k6 대조: <차이가 있으면 건수와 원인(클라이언트 타임아웃 후 서버 커밋 등)>

**성능 (3회 범위)**

- 핵심 그래프/스크린샷: <Grafana 패널 링크, 비교 화면 캡처, 무대 GIF>
- 예측과 대조: 맞음 / 부분적으로 맞음 / 틀림

## 5. 원인

- 관찰된 메커니즘: <무엇이 일어났는지, 근거 지표와 함께. 예: "pg_locks 대기 수가 X로 늘고 wait_event=Lock:transactionid가 지배적">
```

## 작성 가이드

- **코드 실험실을 읽은 뒤 "왜 이 코드인가"를 자기 말로 쓴다.** 원인 절(7)에는 학습 화면의 `why`를 옮겨 적지 말고, 실측 지표로 확인한 내용을 쓴다.
- **가설은 틀릴 수 있게 쓴다.** "성능이 좋아질 것이다"는 반증 불가. "앱 2대에서 `no-lock`은 3회 모두 위반 > 0, `row-lock`은 0, `row-lock`의 p99는 `conditional-update`보다 높다"처럼.
- **정상 상태는 숫자로.** 기준선 실행 runId를 함께 적는다. 카오스 실험의 판정은 "정상 상태로 돌아왔는가, 얼마나 걸렸는가"다.
- **영향 범위와 중단 조건은 카오스·과부하 실험에서 생략하지 않는다.** 로컬이라도 호스트 자원 고갈로 다른 실행 데이터가 오염될 수 있다.
- **원인은 지표로 증명한다.** "락 때문인 것 같다"가 아니라 어떤 뷰·지표·trace에서 무엇을 봤는지.
- **같은 계측 수준끼리만 비교한다.** 다르면 노트에 명시하고 결론을 약하게 쓴다.
- **락 시나리오는 PG 락 프로브 on/off 대조 실행을 포함한다.** `pg_locks` 조회 자체가 lock manager의 락을 잡아 측정 대상을 건드릴 수 있다.
- **웜업은 별도 k6 실행으로 뺀다.** k6 summary·HTML은 한 실행 전체를 집계하므로 같은 실행에 웜업이 있으면 그 값에 섞인다.
- **closed 모델 결과의 지연 수치는 인용하지 않거나 "해석 주의"를 붙인다**(coordinated omission).
- 3회 범위가 넓으면("불안정" 배지) 결론을 내리기 전에 원인을 먼저 찾는다(백그라운드 부하, 웜업 부족, 데이터 캐시 상태).
